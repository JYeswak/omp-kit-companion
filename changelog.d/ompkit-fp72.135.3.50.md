### Fixed

- The bead-lint update gate admits a content edit that repairs a failing bead without making it pass: when the checks the bead fails afterwards are a strict subset of the checks it fails now, the edit lands with a `LINT_REPAIR_ADMITTED` note naming what it cleared and what still fails. Before, a description repair was refused whenever an unrelated failure remained, even one only a checker change could clear. An edit that adds a failure or repairs nothing is still refused, and a content edit combined with `--claim` or `--status` gets no repair admission. (ompkit-fp72.135.3.50)
- Claiming a bead now needs a bead-lint PASS, as Joshua required (J-2026-10-25-107: no worker picks up a bead that does not pass bead lint). `br update --claim`, and a move to `in_progress` in any spelling (`--status in_progress`, `-s in_progress`, `--status=in_progress`), is refused naming the failing checks; repair the bead first with a content-only edit. Before, claims were never linted. Every id of a multi-id `br update` is judged. A claim the gate cannot judge (helper missing, tracker unreadable, timeout) is refused instead of allowed; content edits keep the warn-and-allow behavior. When a claim is refused for custody too (another holder), the custody refusal is shown first. Parking, priority and other workflow moves are not gated. Not covered: a `br` write made from inside an eval subprocess does not pass through this guard. (ompkit-fp72.135.3.50)
