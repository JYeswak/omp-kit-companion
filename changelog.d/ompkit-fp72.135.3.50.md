### Fixed

- The bead-lint update gate admits a content edit that repairs a failing bead without making it pass: when the checks the bead fails afterwards are a strict subset of the checks it fails now, the edit lands with a `LINT_REPAIR_ADMITTED` note naming what it cleared and what still fails. Before, a description repair was refused whenever an unrelated failure remained, even one only a checker change could clear. An edit that adds a failure or repairs nothing is still refused, and a content edit combined with `--claim` or `--status` gets no repair admission. (ompkit-fp72.135.3.50)
- Claiming a bead now needs a bead-lint PASS, as Joshua required (J-2026-10-25-107: no worker picks up a bead that does not pass bead lint). `br update --claim` is refused naming the failing checks, and so is every status native br stores as `in_progress`: `--status IN_PROGRESS`, `inprogress`, `-s`, and short clusters such as `-qs in_progress`. Repair the bead first with a content-only edit. Before, claims were never linted. A status the shell expands at run time (`--status "$S"`) is refused before it runs, because a claim cannot be ruled out. Every id of a multi-id `br update` is judged. A claim the gate cannot judge (helper missing, tracker unreadable, timeout) is refused instead of allowed; content edits keep the warn-and-allow behavior. When a claim is also refused for custody (another holder), the custody refusal is shown first. Parking, priority and other workflow moves are not gated, and neither is `in-progress`, which native br stores as a custom status. A `--status IN_REVIEW` move now meets the review admission like `in_review`. Not covered: a `br` write made inside an eval subprocess does not pass through this guard. (ompkit-fp72.135.3.50)
