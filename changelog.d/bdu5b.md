### Fixed
- The scheduled scratch reaper no longer sits in a blocked open until its 30 minute cap (NFSPROBE1, CHECKOUTBUDGET1). The real cause of the `TIMEOUT` every run since 2026-11-04 was not the size of the census: a process launched by launchd cannot open() or list anything on the user's ovnfs NFS mount (`/Users/josh/checkouts`, a `hard,intr` NFS mount) or on an external volume under `/Volumes` (`stat` answers, every open blocks until a signal; measured with `ls`, `head`, `cat`, python and bun in a LaunchAgent whatever its ProcessType, Nice, LowPriorityIO or SessionCreate, while the same calls answer in 50 ms from a shell). The reaper's worker called `realpath` on its first checkout root and never returned, so the receipt said `interruptedAction: null`. The job now lists the network and `/Volumes` mounts, probes each with its own binary under an 8 s deadline before touching any root (a platform binary such as `ls` is denied a removable volume at once while the kit's binary blocks, so `ls` is not a valid probe), never discovers or scans a root under a blocked mount, skips the checkout inventory when one is blocked, and reports every blocked mount as `blockedMounts` in its result and `network-mount-blocked` in the checkout verdict. A launchd-launched run finished in 177 s with 35 roots scanned; scratch on a blocked mount (the ovnfs checkouts, 351 GB of logical bytes at the last census) is reclaimed only by a run from a shell.
- A scratch-reaper run no longer fails because it refused to touch something still in use (REAPFAIL1). A final recheck that finds a dir with an open file descriptor or a changed owner (`owner-released-but-open-fds-present`, `owner-changed-after-initial-check`, `owner-release-changed-after-initial-check`) is the safety working: it is counted in `refused_count` and the run can end `COMPLETE` with exit 0, while a delete or quarantine error, missing lsof evidence or a rollback failure still fails the run (PeachLeopard AM92344, ompkit-1ra0d.255 [c]).
